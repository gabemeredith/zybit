# Lighthouse Phase 1 — Playwright-driven personas on real OSS sites

> Status: planning. No code yet.
> Parent doc: [`LIGHTHOUSE.md`](./LIGHTHOUSE.md) — read sections 1–5 first.

---

## 1. Goal

Produce **paired (website, PostHog events) data** that:

1. Has **real rendered HTML** Zybit can snapshot.
2. Has **real PostHog autocapture events** generated by interacting with that HTML.
3. Spans an **explicit, controlled persona distribution** so the bias is one we set, not one we inherit.

Without this, the rest of Lighthouse can't verify the loop end-to-end — every other strategy either fakes the events (no autocapture realism) or fakes the HTML (no snapshot realism). Pairing them is the credibility hinge.

---

## 2. Why this approach

See [`LIGHTHOUSE.md` §5](./LIGHTHOUSE.md) for the full reasoning. Short version: we cannot get real customer event streams pre-customer, so we manufacture them — but by driving Playwright through a real PostHog-instrumented site, the **shape** of the events (autocapture selectors, event types, session structure) matches what a real customer's data will look like. The simulation is in the persona behavior, not in the event schema.

---

## 3. Definition of done

By the end of Phase 1 a dev can run:

```bash
npm run lighthouse:phase1 -- --site cal-com --personas balanced --sessions 500
```

…and see:

1. A local instance of cal.com running (or whichever site) with PostHog autocapture wired up.
2. 500 Playwright-driven sessions playing out against it, distributed across personas.
3. Real PostHog events landing in the Lighthouse PostHog project.
4. Those events pulled into Zybit's `phase1_events` table via the existing PostHog connector (`/api/phase2/cron/sync-posthog`).
5. The site's pages captured into `phase2_page_snapshots` via the existing snapshot fetcher.
6. A `Scenario` manifest (TS file under `src/lib/lighthouse/scenarios/`) that references the site + persona mix + expected findings.

No assertions yet — Phase 1 is about getting the data into the system. Assertions land in Phase 3 per [`LIGHTHOUSE.md` §7](./LIGHTHOUSE.md).

## 5. Step-by-step build

### Step 5.1 — Pick the OSS site shortlist

Eight to fifteen sites, **chosen to span an industry × stack matrix**, not chosen for ease. Starter list (all open source, MIT/Apache or similar):

| Bucket | Candidate | Stack | Why include |
|---|---|---|---|
| SaaS landing+app | Cal.com | Next.js SSR | Common reference; rich funnel (signup, booking) |
| SaaS landing+app | Supabase | Next.js SSR | Marketing + console; complex CTAs |
| SaaS landing+app | Plausible | Phoenix/Elixir | Non-Next stack; tests our SPA assumptions |
| SaaS landing+app | Dub | Next.js | Short, fast funnel |
| Ecom | Medusa demo storefront | Next.js | Product → cart → checkout |
| Ecom | Saleor storefront | Next.js | Alternative ecom data shape |
| Ecom | Shopify Hydrogen starter | Remix | Different framework |
| Content/marketplace | Ghost demo | Node/Handlebars | Content reading patterns |
| Content/marketplace | Outline (knowledge base) | React | Internal-tool pattern |
| Marketing/static | shadcn-ui examples | Next.js static | Clean-design baseline |
| Marketing/static | A Tailwind UI starter template | Next.js static | Same |
| SPA edge | A deliberately JS-heavy SPA (Vite + react-router) | Vite SPA | Forces snapshot fetcher SPA fallback |
| Degraded variant | A forked landing page with intentionally bad UX (extra CTAs, weak hierarchy) | n/a | Seeds pain-rule positives |

**Pick ≥1 per bucket for Phase 1; the others can land in Phase 4.** Document choices in `lighthouse/sites/README.md`.

### Step 5.2 — Get each site running locally

For each site:

1. Clone the repo into `lighthouse/sites/<slug>/` (gitignored — these are upstream, not our code).
2. Follow the upstream README to get it running on a local port.
3. Bind each site to a distinct port (`cal-com → 4001`, `supabase → 4002`, etc.) and a distinct hostname via `/etc/hosts` (e.g. `cal-com.lighthouse.local → 127.0.0.1`). The hostname matters because Zybit identifies sites by domain.
4. Add a `lighthouse/sites/<slug>/manifest.json` capturing: port, hostname, primary funnel paths, expected conversion event, framework. This is what the persona DSL reads from.

**Do not modify upstream source.** All instrumentation goes through env vars and a thin wrapper script that injects the PostHog snippet.

### Step 5.3 — Add PostHog autocapture

1. Create a single PostHog project called "Lighthouse" in a real PostHog cloud account (or self-hosted instance — your call, but cloud is simpler).
2. Grab the project API key.
3. For each site, inject `posthog-js` autocapture with `posthog.init(KEY, { api_host, autocapture: true, capture_pageview: true, person_profiles: 'identified_only' })`.
   - Injection mechanism varies per site. For Next.js apps, a wrapper layout or `_app.tsx` patch. For static sites, a `<script>` tag in the template. Keep the patches in `lighthouse/sites/<slug>/patches/` so they're reviewable.
4. Set a custom `distinct_id` per persona session so Zybit's visitor-ID bridge has something to stitch on.
5. Verify by opening the site manually, clicking around, and confirming events appear in the Lighthouse PostHog project within ~30 seconds.

### Step 5.4 — Persona DSL

Personas are declarative — a TS file describing behavioral traits, not procedural code. This keeps them reviewable and serializable into Scenario manifests.

```ts
// src/lib/lighthouse/personas/types.ts
export interface Persona {
  id: string;                 // 'power-user', 'casual', 'churning', 'evaluator', 'bot-ish'
  weight: number;             // share of sessions assigned this persona (0..1)
  sessionsPerVisit: { min: number; max: number };
  pagesPerSession: { mean: number; stddev: number };   // log-normal
  dwellMsPerPage: { mean: number; stddev: number };    // log-normal
  scrollDepthPct: { mean: number; stddev: number };    // 0..100
  clickIntent: number;        // probability of clicking a CTA when present (0..1)
  formSubmitIntent: number;   // probability of completing a visible form (0..1)
  bounceProbability: number;  // probability of leaving after 1 page (0..1)
  preferredPaths: string[];   // weighted bias toward these path prefixes
  diurnalWindowUtc: [number, number]; // hour-of-day band for activity
}
```

Ship five personas to start: `power-user`, `casual`, `churning`, `evaluator`, `bot-ish`. Pin their numbers explicitly with a comment citing the source distribution (Baymard, NN/g, Contentsquare benchmarks, or "internal guess — calibrate against source 4 in §6 once we have it").

### Step 5.5 — Playwright driver

The driver is the loop: pick persona by weighted sample, open a `BrowserContext`, simulate a session by sampling from the persona's distributions, close the context. One file:

```ts
// src/lib/lighthouse/generators/playwrightDriver.ts
export async function runSession(opts: {
  siteManifest: SiteManifest;
  persona: Persona;
  distinctId: string;
  now: Date;
}): Promise<void>
```

Implementation notes:

1. Use a single Playwright browser, many `BrowserContext`s — one context per session — for isolation without the cold-start cost.
2. Set `distinct_id` via a cookie or via `page.addInitScript` before navigation, so PostHog picks it up on first event.
3. Sample dwell from log-normal; never use uniform random. Set timeouts conservatively (max 60s per page) so a runaway session can't stall a batch.
4. Scroll behavior: `page.evaluate(() => window.scrollTo(...))` in steps matching `scrollDepthPct`. Autocapture picks up scroll if configured; if not, dispatch a custom `$scroll` event.
5. Click selection: query all `a, button, [role=button]` on the page, weight by the persona's `preferredPaths`, pick one, click. Don't click destructive things (look for `data-testid="delete"` etc. and skip them).
6. Form completion: when persona's `formSubmitIntent` fires and a `<form>` is visible, fill fields with persona-tagged synthetic values and submit. Use deterministic seeded faker so re-runs are reproducible.
7. Diurnal windowing: when seeding 30 days of history, schedule session timestamps within the persona's `diurnalWindowUtc` with a sine envelope.
8. Determinism: seed every random draw from `hash(scenarioId + sessionIndex)` so a re-run produces the same events. Document this loudly.

### Step 5.6 — Verify events land in PostHog

After a small batch (10 sessions, 1 persona, 1 site):

1. Open the Lighthouse PostHog project's live events feed. Confirm pageviews, clicks, and the custom distinct_ids are present.
2. Check session structure: 5–30 events per session, clustered in time, then quiet. If you see uniform-spaced events, persona dwell sampling is broken.
3. Spot-check autocapture selectors against the site's actual DOM. If PostHog is capturing `button[class="x-3f4a"]` rather than `[data-testid="signup-cta"]`, the upstream site needs better selectors *or* you need to bias the driver toward stable selectors. Don't paper over this — Zybit's audit rules read selectors.

### Step 5.7 — Pull events back into Zybit

Use the existing PostHog connector — do not write a parallel path.

1. In Zybit, create a `phase1_sites` row for each Lighthouse site (slug-prefixed `lighthouse_*` so it's isolated).
2. Create a `phase2_integrations` row with `provider='posthog'`, the Lighthouse PostHog project id, and a `secretRef` pointing to an env var that holds the read-only PostHog personal API key.
3. Trigger `/api/phase2/cron/sync-posthog` manually (`curl` the cron route with the cron secret) and confirm rows land in `phase1_events` with the right `siteId`, `source='posthog'`, and a populated `sourceEventId` for dedupe.
4. Run `/api/phase2/cron/sync-snapshots` (or whatever the snapshot trigger route is) to populate `phase2_page_snapshots` from the locally-running site's URL.

Both are existing crons. Phase 1 is about *exercising* them with synthetic input, not building anything new on the Zybit side.

### Step 5.8 — Wire into Scenario format

Final step: produce a `Scenario` manifest that ties everything together.

```ts
// src/lib/lighthouse/scenarios/cal-com-balanced.ts
import type { Scenario } from '../types';
export const calComBalanced: Scenario = {
  id: 'cal-com-balanced',
  name: 'Cal.com with balanced persona mix, 30d history',
  organization: { id: 'lighthouse_org_cal_com', name: 'Cal.com (Lighthouse)', plan: 'starter' },
  site: { id: 'lighthouse_site_cal_com', url: 'http://cal-com.lighthouse.local:4001', meta: { mrr: 50_000_00, aov: null, sessionCount: 0 } },
  integrations: [{ provider: 'posthog', projectId: 'lighthouse', /* ... */ }],
  siteConfig: { /* cohort/CTA/narrative declarations */ },
  pages: [],   // populated at snapshot time
  events: [],  // populated by the cron pull
  expected: { findings: { mustFire: [], mustNotFire: [] } },  // empty until Phase 3
};
```

The CLI wraps the whole thing:

```bash
npm run lighthouse:phase1 -- --site cal-com --personas balanced --sessions 500 --history 30d
```

…which (a) ensures the site is running, (b) runs the persona-weighted Playwright driver, (c) triggers the PostHog + snapshot crons in Zybit, (d) writes/updates the Scenario manifest.

## 7. Bias controls (do not skip)

The whole point of this approach is *controlled* bias. The risks:

- **OSS-site bias**: dev-tools-SaaS over-representation. Counter: ≥30% ecom and ≥10% content/marketplace in the Phase 1 site shortlist.
- **High-quality-design bias**: OSS landing pages are too well designed; pain rules never fire. Counter: include the degraded-variant site (Step 5.1 row 13) from day one.
- **English/US bias**: audit rules touch language detection and currency math. Counter: at least one non-English site and one non-USD ecom site in Phase 1.
- **Persona uniformity**: if every persona converts at the same rate, the outcome math is bored. Counter: span 3× in `clickIntent` and `formSubmitIntent` across the five personas.
- **Volume bias**: if every scenario is ~5k events, neither high-traffic rollup paths nor low-traffic confidence-bound math gets exercised. Counter: ship one scenario at ~500 sessions, one at ~5k, one at ~50k.

Track coverage in `src/lib/lighthouse/coverage/matrix.ts` and print uncovered cells via `npm run lighthouse:coverage`. Even if 80% of the matrix is empty at end of Phase 1, the *visibility* of the gap is the deliverable.

## 9. Open questions

1. **PostHog Cloud vs self-hosted for the Lighthouse project?** Cloud is simpler; self-hosted means events never leave our infra. Decide before Step 5.3.
2. **How do we keep the OSS sites up to date?** Pin upstream commits in `manifest.json` and re-run periodically. Don't auto-update — upstream changes break personas silently.
3. **Where does the Lighthouse PostHog API key live in prod?** Probably as `LIGHTHOUSE_POSTHOG_API_KEY` env var, referenced by `phase2_integrations.secretRef`. Same pattern as customer integrations.
4. **Do we need a synthetic origin for the proxy/Test step?** Not in Phase 1 — Test verification is Phase 3+. But the locally-running sites are the natural candidate when we get there.
5. **Seed determinism guarantee** — should `npm run lighthouse:phase1` always produce byte-identical PostHog events on re-run? Probably yes for the driver's random draws; PostHog's own server-side timestamps will differ. Document this.
